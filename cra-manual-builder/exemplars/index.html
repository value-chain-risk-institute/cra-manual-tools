CRA Example-Product Coverage Matrix

Which example products does a CRA user-manual template suite need? Realms multiply forever — axes don't. This page defines the dimensions that actually change what a manual must say, then picks the smallest exemplar set that covers every value of every axis at least once.

Method (borrowed from test engineering): enumerate the axes whose value changes the manual's content or audience; select exemplars for coverage, not for popularity. Twelve in-scope products + two boundary cases cover all values below. Any real product then maps to its nearest exemplar.

The eight axes

A · CRA classRegulatory classification Default · Important Class I · Important Class II · Critical · Out of scope conformity-assessment route; depth of the security-properties section; CE-marking narrative.
B · AudienceWho reads the manual Lay consumer · Child-adjacent user · Installer / integrator · Trained operator · OEM engineer (B2B component) language level; Pxx vs CUxx balance; whether "conditions of use" are instructions or contractual integration requirements.
C · FormProduct form Hardware + firmware · Embedded component / module · Device + app + cloud · Pure software · Open source w/ steward SBOM presentation; what "the product" even is; steward vs manufacturer obligations.
D · RadioRED relevance Radio equipment (RED 3.3 d/e/f lineage) · Wired-only · N/A (software) interplay statement with RED delegated-act history; spectrum-related conditions of use.
E · ConnectivityConnectivity model Cloud-dependent · Local network only · Air-gapped capable · Fully offline remote-data-processing disclosures; what happens at end of cloud service; offline fallback behavior.
F · UpdatesUpdate delivery path OTA automatic · Store/package distributed · Manual / technician · Safety-recertification constrained update instructions; user consent language; the OT case where patching collides with functional-safety certification.
G · LifecycleSupport horizon Short (<3y) · Medium (5–10y) · Long (15y+) support-period statement; spare-parts/firmware availability; end-of-life and secure-disposal guidance.
H · ScopeScope boundary In scope · Exempt via sectoral law (MDR, vehicle type-approval, …) nothing — and that's the point: boundary exemplars teach template users where the CRA manual is not the right document.

Coverage check — every axis value, at least one exemplar

A · Class
  • Default → PLC, EV charger, HVAC
  • Important I → doorbell, toy, wearable, router, password manager
  • Important II → firewall
  • Critical → secure element, smart meter gateway
  • Out of scope → BP monitor, telematics
B · Audience
  • Lay consumer → doorbell, wearable, router, password manager
  • Child-adjacent → toy
  • Installer/integrator → smart meter gateway, HVAC
  • Trained operator → firewall, PLC
  • OEM engineer → secure element, crypto library
C · Form
  • HW+firmware → router, firewall, PLC, HVAC, meter gateway
  • Embedded component → secure element
  • Device+app+cloud → doorbell, toy, wearable
  • Pure software → password manager
  • OSS + steward → crypto library
D · Radio / E · Connectivity
  • Radio → doorbell, toy, wearable, router, meter gateway, EV charger
  • Wired-only → firewall, PLC, secure element
  • Cloud-dependent → doorbell, toy, EV charger
  • Local-only → router, firewall, HVAC
  • Air-gapped → PLC · Offline → secure element
F · Updates
  • OTA → doorbell, toy, wearable, router, EV charger
  • Store/package → password manager, crypto library
  • Manual/technician → meter gateway, HVAC, firewall
  • Safety-recert constrained → PLC
G · Lifecycle / H · Scope
  • Short → doorbell, toy, wearable
  • Medium → router, firewall, password manager
  • Long → PLC, EV charger, HVAC, meter gateway, secure element
  • Exempt boundary → BP monitor (MDR), telematics (type-approval)
Two notes for the working group. (1) Class assignments were verified against the final text of Regulation (EU) 2024/2847, Annexes III/IV, on 17 July 2026. Two corrections were made in that pass and are worth knowing: the smart doorbell camera is Important Class I (Annex III lists smart home security products including security cameras), and the PLC is Default class — PLCs appear nowhere in the final Annex III, having been removed from earlier drafts. The Commission's implementing regulation on technical descriptions for Annex III/IV categories may further refine boundaries; treat it as the tie-breaker for edge cases. (2) The set optimizes for manual-content coverage, not market importance — a deliberately boring CAD desktop application could replace the password manager if the group prefers a non-security pure-software exemplar (Default class), at the cost of losing an Important-I software case.

How to use this

For each exemplar, the group writes (or the CRA Manual Builder generates) one reference manual. A manufacturer approaching the template then maps their product to its nearest exemplar by walking the axes — not by guessing which "realm" they belong to. If a real product hits an axis-value combination no exemplar covers, that's a signal to extend the set, and the matrix shows exactly which cell is missing.
